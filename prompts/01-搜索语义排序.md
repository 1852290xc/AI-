# Prompt 记录 01 · 搜索的语义排序与个性化

> 真实开发记录：本项目的搜索功能是分三次迭代做出来的。
> 每次迭代都能对应到仓库里的提交，时间戳可查。

## 背景

原始搜索是 `LIKE` 匹配：搜「键盘」只能命中标题里带「键盘」的商品，
搜「便宜的平板」一条都出不来——因为「便宜」这个词商品标题里根本没有。

## 迭代 A：先把「能搜到」解决

**需求原话**

> 搜索没有结果，用户搜「便宜的平板」什么都出不来。

**给 AI 的指令（节选）**

```
搜索改成相关性排序，不要 LIKE。
要求：
1. 中文分词用二元组，英文按词切；
2. TF-IDF + 余弦相似度，标题权重高于描述；
3. 「便宜的平板」这类口语要能命中 iPad，靠同义词表扩展；
4. 没有命中的词不要硬凑结果，返回空列表，前端提示「换个说法」。
```

**AI 的第一版问题**

- 单字查询（如「灯」）零命中：分词只产出二元组，而「台灯」在索引里只有 `台灯`，没有 `灯`
- 结果空的时候用「猜你喜欢」兜底，把 15 件商品全塞进搜索结果

**我怎么引导修复**

```
问题 1：搜「灯」返回 0 条，但库里有「宿舍护眼台灯」。
原因：索引只有二元组，没有单字。请在索引里补上单字，但排除停用词。
问题 2：搜索无结果时不要用推荐兜底，用户会觉得搜坏了。
无结果就返回空，前端已经有「换个说法」的提示。
改动要能通过这两个用例：q=灯 命中台灯；q=空调 返回 0 条。
```

**结果**：`search_engine.py` 建立；对应提交 `25a5ebc feat(search): 本地语义检索引擎`。

## 迭代 B：相关性要带「为什么」

**需求原话**

> 用户搜索时算法自动推送用户喜欢的商品。

**给 AI 的指令**

```
在语义分之上叠加个性化，权重写死并公开：
  0.60 语义相似度 + 0.25 分类偏好 + 0.15 热度
分类偏好取 Behavior 表里该用户最近 60 条浏览的分类占比。
每条结果必须给一个可读理由：命中词 / 常看品类 / 热门，三选一。
理由要显示在卡片上，让用户知道为什么推给他。
```

**AI 的输出**：排序与理由都实现了，但**理由文案错位**——
搜「键盘」时第二件结果显示「匹配『键帽、机械、键盘』」，
而这件是鼠标，命中的其实是描述里的「适合图书馆用」被分词成了无关词。

**我怎么引导修复**

```
理由取的是 query 与 doc 的交集 token，但 token 太长（三个字以上）就不可读了。
改成：只取长度 2–4 的词，最多 3 个；如果交集为空，退回「你常看{品类}」。
另外加一条：理由文字不超过 12 个字，避免卡片被撑开。
```

**结果**：提交 `175bc6c feat(search): 搜索接入语义排序与大模型可选的查询理解/重排`。

## 迭代 C：可选的大模型增强，但不能拖垮主流程

**给 AI 的指令**

```
llm.py 做成可插拔：
- 没配 LLM_API_KEY 时 enabled() 返回 False，全站走本地；
- 配了就用它做查询理解和重排；
- 超时 6 秒、任何异常都返回 None，调用方自动回落；
- 结果缓存 5 分钟，避免同一查询反复计费。
不要让 AI 失败导致页面 500。
```

**AI 的第一版问题**：`_chat()` 没有 try/except，网络一断直接抛异常到路由层。

**修复**：把网络调用包在 `run()` 里 try/except，异常返回 None；
调用方写成 `expanded = llm.expand_query(q) if llm.enabled() else None`，
None 就等于「没这回事」，继续用本地结果。

**结果**：`llm.py` 落地；提交 `175bc6c`，测试补到 28 项全过。
